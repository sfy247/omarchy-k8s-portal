# Kubernetes networking and the gateway

Back to [Home](index.md). DNS and certificates are covered in depth in [05 DNS and TLS](05%20DNS%20and%20TLS.md).

## The big picture

There are four layers of networking, from outside to inside:

1. **Laptop.** Lab names resolve to loopback IPs; each cluster owns one.
2. **Docker.** Every kind cluster is a container on Docker's `kind` network.
   kind publishes chosen node ports onto your loopback IPs.
3. **Cluster.** Standard Kubernetes networking: pods, Services, CoreDNS.
4. **Gateway.** Envoy terminates TLS and routes by hostname to the right Service.

## Port map

Each cluster publishes ports on its **own** loopback IP, so all of them can use
80 and 443 at once. Raw NodePorts are also published on `127.0.0.1` for
debugging.

| Cluster | Loopback IP | :80 → NodePort | :443 → NodePort | Debug NodePorts on 127.0.0.1 |
|---|---|---|---|---|
| mgmt (hub) | 127.0.0.10 | 31080 | 31443 | 30080 (Argo CD, plain HTTP) |
| dev | 127.0.0.11 | 31080 | 31443 | 30001–30010 |
| staging | 127.0.0.12 | 31080 | 31443 | 30101–30110 |
| prod | 127.0.0.13 | 31080 | 31443 | 30201–30210 |

All of these numbers are settings in `lab.yml` (`lab_hub_ip`,
`lab_environments[].ip`, `lab_gateway_node_ports`, `lab_app_node_port_range`).

## The gateway (Gateway API + Envoy Gateway)

the **Gateway API**, implemented by **Envoy Gateway**. The same setup runs in
every cluster, installed by Argo CD from `cluster-addons/`.

| `GatewayClass envoy` | gateway chart | Says "Envoy Gateway implements gateways of this class" |
| `EnvoyProxy envoy` | gateway chart | Makes the proxy Service a NodePort with fixed ports kind can map |
| `Gateway shared` | gateway chart | Two listeners; HTTPS accepts routes from **all** namespaces, HTTP only from its own (the redirect) |
| `Certificate shared-tls` | gateway chart | Wildcard cert for the listener hostname, issued by the `lab-ca` ClusterIssuer |
| `HTTPRoute https-redirect` | gateway chart | Every HTTP request → `301` to HTTPS |
| `HTTPRoute <app>` | web-service chart | `<app>.<env>.<domain>` → that app's Service |
| `HTTPRoute argocd` | gateway chart (hub only) | `argocd.<domain>` → `argocd-server` |

The gateway's hostname and NodePorts aren't in Git. Ansible writes them as
annotations on each cluster's Argo CD registration, and the `gateway`
ApplicationSet passes them to the chart (see [04 GitOps and Argo CD](04%20GitOps%20and%20Argo%20CD.md)).

All kind clusters share Docker's `kind` network, so Argo CD on the hub reaches a
worker's API server by its **container name**:

The hub→worker connection is drawn in [02 Kubernetes Setup and Structure](02%20Kubernetes%20Setup%20and%20Structure.md).

The hub itself is registered as `mgmt` at `https://kubernetes.default.svc`
(in-cluster), so add-ons can target it like any other cluster.

## Inside a cluster

| Piece | What it is |
|---|---|
| CNI | **kindnet** (kind's default). Pod CIDR `10.244.0.0/16`. Supports NetworkPolicy. |
| Services | `10.96.0.0/12`, implemented by kube-proxy |
| DNS | CoreDNS: `python.hello-world.svc.cluster.local` |
| NetworkPolicy | One per app: ingress only on its HTTP port; egress only to CoreDNS (UDP/TCP 53) |

What each app's NetworkPolicy allows is drawn in [02 Kubernetes Setup and Structure](02%20Kubernetes%20Setup%20and%20Structure.md).

> [!tip] Debugging a route
> `kubectl --context kind-dev -n hello-world get httproute` shows each route's
> hostname. `kubectl --context kind-dev -n gateway describe gateway shared`
> shows whether the listeners are `Programmed` and how many routes are attached.
